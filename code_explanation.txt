================================================================================
PRODUCTION-GRADE HYBRID PDF RAG PIPELINE
System Architecture, Component Mechanics, and Heuristics Explained
================================================================================

This document provides a highly detailed, interviewer-level breakdown of the 
entire codebase. It covers design patterns, mathematical and algorithmic 
heuristics, layout reconstruction techniques, and search mechanics.

--------------------------------------------------------------------------------
1. HIGH-LEVEL ARCHITECTURE OVERVIEW
--------------------------------------------------------------------------------
The system is built as a modular, production-grade PDF processing and RAG 
(Retrieval-Augmented Generation) pipeline. It separates document parsing (layout 
and table extraction) from downstream vector ingestion and LLM querying.

2. COMPONENT DIRECTORY & FILE PURPOSE
--------------------------------------------------------------------------------
- main.py: Entry point. Features CLI commands (ingest, query, interactive, info, 
  reset) with a progress bar and terminal UI tables powered by the 'rich' package.
- config.py: Central config using python-dotenv. Manages GROQ api credentials, 
  model parameters, vector sizes, chunking settings, and OCR DPI.
- pdf_processor/
  - classifier.py: Classifies PDF pages as 'digital' or 'scanned'.
  - digital_extractor.py: Digital text parsing and table extraction using 
    pdfplumber, with Tesseract fallback.
  - ocr_extractor.py: Image pre-processing and raw OCR fallback using pytesseract.
  - table_extractor.py: Table structure parsing, spatial clustering, and text 
    filtering using Tesseract's word-level TSV data.
- rag/
  - chunker.py: Splits parsed text and tables into semantically relevant chunks.
  - embeddings.py: Generates dense (MiniLM) and sparse (BM25) vector embeddings.
  - vector_store.py: Handles collection creation, embedded Qdrant indexing, 
    upserts, and search operations.
  - retriever.py: Executes hybrid retrieval and merges sparse and dense rankings 
    using Reciprocal Rank Fusion (RRF).
  - generator.py: Formats retrieved chunks and prompts the Groq LLM.
- utils/
  - markdown_utils.py: Converts 2D list rows into clean markdown tables.

3. PAGE CLASSIFICATION HEURISTIC
--------------------------------------------------------------------------------
Every page is processed independently because PDFs frequently contain a mix of 
digitally typed pages and scanned pages (images, printouts, or receipts).

- Mechanics:
  1. We attempt to extract text from the page using pdfplumber's `page.extract_text()`.
  2. If the length of the trimmed extracted text is greater than or equal to the 
     `SCANNED_TEXT_THRESHOLD` (set to 30 characters in config.py), we classify 
     the page as "digital".
  3. If it is less than 30 characters, the page is classified as "scanned".
- Why this threshold?
  A scanned page with minor noise might output a few garbage characters. By 
  setting a minimum threshold of 30, we ensure that empty pages, signature pages, 
  and fully scanned images are not misclassified as digital pages (which would 
  result in empty text extraction).

4. THE EXTRACTION PIPELINE (THE CRITICAL CODE MECHANICS)
--------------------------------------------------------------------------------

A. Digital Extraction Loop (`digital_extractor.py`)
1. Extract Tables First:
   We extract tables first because we must prevent table cell text from being 
   swallowed into the body text. We run `_extract_tables_structured()` using 
   pdfplumber's horizontal and vertical line detection.
2. Contamination Filter:
   If a table has oversized cells (max cell length > 300 characters), it is 
   likely that pdfplumber grouped a large body text block into a false table. 
   We discard these invalid tables.
3. Fallback Tesseract Table Extraction:
   If pdfplumber returns 0 tables (e.g. for borderless tables or tables inside 
   embedded images on the digital page), we fall back to Tesseract OCR table 
   extraction. We render the page as a 300 DPI image, pass it to Tesseract, 
   detect the table regions, and map the image pixel bounding boxes back to 
   PDF points using coordinate scale factors:
     x_scale = page_width (PDF points) / image_width (pixels)
     y_scale = page_height (PDF points) / image_height (pixels)
4. Text Filtering & Bounding Box Padding:
   Using the bounding boxes of the detected tables (both from pdfplumber and 
   Tesseract fallbacks), we filter out all characters inside these boxes before 
   extracting the body text. To prevent first or last characters of table rows 
   (e.g., "D", "R", "F", "Y") from being left behind due to slight alignment 
   inaccuracies, we expand each bounding box in PDF points:
     x0 = x0 - 15, y0 = y0 - 5, x1 = x1 + 15, y1 = y1 + 5
   We run pdfplumber's `page.filter(...)` using these padded bounding boxes.
5. Garbled Text Cleaning:
   If the remaining text contains more than 30% single-character lines, we 
   classify it as garbled (typically caused by horizontal watermarks or rotated 
   text) and filter out all single-character lines.

B. Layout and Table Reconstruction (`table_extractor.py`)
This is the core algorithm that processes a page image and converts layout grids 
into Markdown tables.

1. Tesseract `image_to_data` DF:
   We run Tesseract with Page Segmentation Mode (PSM) 6 (`--psm 6`, treat the 
   image as a single uniform block of text). This returns a DataFrame containing 
   every word with its page coordinates (`left`, `top`, `width`, `height`), 
   block number, line number, word number, and confidence.
2. Word Grouping into Rows:
   Words are sorted by vertical y-coordinates. They are binned into rows using 
   a vertical tolerance:
     y_tolerance = image_height * 0.012 (1.2% of page height)
   If a word's center y-coordinate deviates from the current row's baseline 
   by more than 1.2%, it starts a new row.
3. Counting Column Boundaries:
   We calculate the gaps between adjacent words in a row to determine how many 
   columns the row contains:
     gap = curr_word_left - (prev_word_left + prev_word_width)
   If `gap > col_gap` (where `col_gap = page_width * 0.02`), it represents a 
   column gutter gap, and we increment the column count. Since regular sentences 
   only have tiny spaces (typically < 1% of page width), they result in 
   `col_count = 1`. Table rows result in `col_count >= 2`.
4. Block Grouping & Proximity:
   Rows are clustered vertically into blocks. A new row is added to the current 
   block if the vertical gap between their centers is less than:
     max_gap = max(avg_word_height * 8.0, image_height * 0.08)
   However, if the next row is a single-column row (cols=1) and its gap is 
   larger than `max_line_gap = avg_word_height * 2.5`, we split the block. 
   This prevents a table block from swallow paragraph lines.
5. Word-Count and Propagation Trimming Heuristic:
   Sometimes a paragraph ending right above the table or a page footer right 
   below it is grouped into the block. We trim these:
   - We check the leading and trailing rows. If they have `col_count < 2` and 
     contain >= 3 words, they are classified as paragraphs and trimmed off.
   - We use **propagation trimming**—once a paragraph row is trimmed, any 
     subsequent adjacent rows with `col_count < 2` are trimmed as well until 
     we hit a multi-column row. This cleanly removes short wrapped paragraph 
     endings (like "market conditions.") while preserving short wrapped cell 
     lines (like "Fulfillment" or "Acquisition") that belong to the table.
6. 2D Table Reconstruction & Columns Clustering:
   To rebuild the table grid, we collect the `left` coordinates of all words 
   in all rows of the block and sort them. We cluster them into column boundaries:
     if curr_x - prev_x > image_width * 0.04 (4% of page width)
   This defines our column boundary positions. For each row, we assign words to 
   cells by placing them in the column boundary index that matches their `left` 
   coordinate. The cells are then converted to Markdown.

C. Scanned Page Extraction
For fully scanned pages, we run:
1. `preprocess_image()`: Convert to grayscale, apply adaptive thresholding 
   for binarization, and execute morphological opening to clean noise.
2. `extract_tables_with_tesseract()`: Extract markdown tables.
3. `extract_text_with_tesseract()`: Run Tesseract `image_to_data`, filter out 
   all words falling inside the table bounding boxes, and reconstruct the 
   remaining words into flowing text using paragraph block indicators.

--------------------------------------------------------------------------------
5. THE HYBRID RAG PIPELINE
--------------------------------------------------------------------------------

A. Recursive Chunking (`chunker.py`)
- We use a recursive character splitter.
- We split on `\n\n` (paragraphs), `\n` (lines), and spaces.
- **Table Handling**: Markdown tables are treated as atomic units. We do not 
  split markdown tables across chunks, because breaking a table row or column 
  destroys its semantic tabular structure. Each table is indexed as a whole.

B. Dual-Embedding Engine (`embeddings.py`)
Hybrid RAG searches across two different vector spaces to combine semantic 
meaning with keyword search:
1. Dense Vector Embeddings:
   - Model: `sentence-transformers/all-MiniLM-L6-v2` (384 dimensions).
   - Captures deep semantic meaning, synonyms, and conceptual relationships.
2. Sparse Vector Embeddings (BM25):
   - Model: `Qdrant/bm25` (via fastembed).
   - Captures exact keyword matching, IDs, codes, names, and jargon.

C. Self-Hosted Embedded Qdrant Database (`vector_store.py`)
- The database runs in **embedded mode** (`QdrantClient(path="./qdrant_data")`), 
  persisting vectors directly to disk inside the python process.
- We configure a single Qdrant collection to index both dense and sparse vectors:
  - Dense configuration: Cosine similarity distance, size 384.
  - Sparse configuration: BM25 sparse vectors.

D. Hybrid Retrieval & RRF Fusion (`retriever.py`)
When a query is entered:
1. We compute its dense embedding (MiniLM) and sparse embedding (BM25).
2. We query Qdrant using two search legs:
   - Leg 1: Dense search (returns top 50 matches).
   - Leg 2: Sparse search (returns top 50 matches).
3. We merge the results using **Reciprocal Rank Fusion (RRF)**:
   The RRF score for a document $d$ is:
     RRF_Score(d) = sum( 1 / (60 + Rank_i(d)) ) for i in {dense, sparse}
   Where `Rank_i(d)` is the 1-based rank of document $d$ in search leg $i$. If a 
   document is not retrieved in a leg, its rank is treated as infinity (score 0).
4. The merged list is sorted by RRF score, and the top 10 chunks are returned as 
   context. RRF is highly robust because it does not require normalizing scores 
   between different distance metrics.

E. LLM Generation (`generator.py`)
The Groq LLM client is configured with `openai/gpt-oss-120b`. It uses a custom 
system prompt instructing the model to answer the user's question strictly 
using the retrieved excerpts (marked with page numbers and document names) 
and format its answers using inline citations (e.g., `【Source 1, Page 2】`).

6. PRODUCTION CONSIDERATIONS & TRADE-OFFS
--------------------------------------------------------------------------------
- Scalability: Running Qdrant in embedded mode is great for local applications 
  but limits concurrent writes. For scale, changing a single config line 
  connects the client to a clustered Qdrant cluster on Kubernetes.
- OCR Performance vs Speed: Processing images via Tesseract can be CPU-heavy. 
  By only calling Tesseract on scanned pages and using pdfplumber on digital 
  pages, we maintain sub-second extraction speeds for digital PDFs.
- Bounding Box Alignment: When converting between PDF points (72 DPI) and 
  rasterized images (300 DPI), floating-point rounding errors are inevitable. 
  Our padded bounding box filter represents a robust production solution to 
  prevent leftover text artifacts.
- API Latency vs RAG Quality: Query rephrasing adds one fast LLM completion 
  round-trip (~200ms on Groq) but dramatically boosts retrieval recall.

7. ADVANCED MECHANICS: TABLE DENSITY HEURISTIC & CONVERSATIONAL MEMORY
--------------------------------------------------------------------------------

A. Table Density & Layout Validation Heuristic
- The Problem: Standard OCR layout segmentation detects horizontal columns for 
  spaced text (like "John Doe | Software Engineer | Github | LinkedIn" or list items 
  with dates). Since these layouts have multiple vertical alignments, the 
  row/column clustering builds high-column sparse table grids where most cells 
  are empty. This causes false-positive table formatting.
- The Solution: We implement `is_valid_table(table_data)` in `table_extractor.py`. 
  This function calculates the density of the table:
    empty_cells = count(cell == "" for cell in table)
    total_cells = rows * cols
    empty_ratio = empty_cells / total_cells
  If `empty_ratio > 0.45` (45% or more cells are empty), the table candidate is 
  invalidated.
- Integration: Discarded regions are removed from `table_bboxes`. This ensures 
  the text in these coordinates is NOT excluded during text extraction, preserving 
  spaced plain text as natural body text instead of losing it.

B. Conversational Memory & State Flow
- Frontend Tracking: The client chatbot UI maintains a global `chatHistory` array. 
  Every user message and assistant response is pushed as a dict: 
    `{ role: "user" | "assistant", content: str }`
- Context resets: The history is automatically cleared when a new PDF is ingested 
  or when the vector index is manually wiped to prevent history contamination.
- Standalone Query Optimization (`rephrase_query`): Before fetching documents, 
  the backend calls Groq to condense the current query using recent context. For 
  example, if history contains "Who is Abhimanyu?" and the follow-up is "What is 
  his CGPA?", the optimizer rephrases it to "What is Abhimanyu's CGPA?". This 
  rephrased query is used for hybrid search.
- Context Generation: The entire conversation history list is passed into the final 
  LLM prompt to preserve context and allow the model to refer to past answers.

8. INTERVIEWER QUESTIONS, CROSS-QUESTIONS, & DEEP DRILLS
--------------------------------------------------------------------------------

Q1: How does the system handle mixed digital and scanned pages within a single PDF?
A: The system uses a hybrid classification pipeline. In `classifier.py`, we run 
   `pdfplumber` to extract digital text. If the text contains fewer than 30 characters, 
   the page is classified as scanned, and we run a full OCR extraction using pdf2image 
   (300 DPI) and Tesseract. If it contains more than 30 characters, we parse it digitally.
   Furthermore, to capture digital pages with embedded screenshots or borderless tables, 
   we run a fallback OCR pathway if pdfplumber detects 0 tables.

[Cross-Question]: What if a page is 90% scanned but has a digital footer or header, 
yielding around 50 digital characters? Your classifier will label it "digital" and 
miss the scanned body! How would you fix this?
[Answer]: That is a classic edge-case. The 30-character threshold works for clean documents, 
but for mixed-composition pages, a better heuristic is calculating "word bounding box density". 
We would render the page as an image, detect text bounding boxes using OpenCV/Tesseract, and 
compare the count of digitally extracted words to the count of OCR-detected visual words. If 
digitally extracted words represent less than 80% of visual words, we classify it as scanned 
or trigger a dual-extraction merge where we align and deduplicate the text layouts.

---

Q2: Why do you perform LLM-based query rephrasing instead of simply concatenating the 
conversation history to the retrieval query?
A: In vector searches (both dense and sparse), search accuracy relies on semantic or 
   keyword overlap. Concatenating history (e.g. "Who is John?" + "Where does he work?") 
   dilutes the search query with irrelevant words ("Who is John"), causing the vector database 
   to retrieve noisy chunks. Passing a raw pronoun-heavy follow-up like "Where does he work?" 
   fails completely because the vector DB cannot resolve "he" to "John". Rephrasing 
   condenses the conversation turn into a standalone query ("Where does John work?"), 
   ensuring high precision and recall during Qdrant lookups.

[Cross-Question]: Rephrasing adds a blocking LLM call before document retrieval, increasing 
user latency. How do you optimize or bypass this step?
[Answer]: In a production system, we can optimize this in three ways:
1. Classification step: Use a lightweight local classifier (e.g. a small fine-tuned BERT 
   model or rule-based parser) to check if the query contains pronouns or requires context. 
   If the query is already standalone, we bypass rephrasing entirely.
2. Parallelization: Run the retrieval query on the raw user query *in parallel* with the 
   rephrasing call. Once rephrasing returns, we fetch any missing semantic chunks and 
   fuse them.
3. Speculative execution: In multi-turn chat, we can preemptively pre-compute likely 
   rephrasings or cache history embeddings.

---

Q3: How does your empty-cell density heuristic validate tables, and what are its failure modes?
A: Our empty-cell heuristic calculates `empty_cells / total_cells`. If more than 45% of 
   the cells in the reconstructed 2D grid are empty, we classify it as spaced text and 
   discard the table formatting. This is extremely effective for resumes or reports 
   containing horizontal layout blocks.

[Cross-Question]: What if the document contains a genuine financial table with many empty 
cells (e.g. a sparse balance sheet or sparse comparison matrix)? Your threshold will 
discard it! How do you handle this?
[Answer]: A pure density heuristic has limitations on sparse genuine tables. To handle this, 
we can upgrade the table validation to look at:
1. Structural lines: If the PDF contains actual drawing/vector lines separating the cells 
   (extracted via `page.rects` or `page.lines` in pdfplumber), we bypass the density check.
2. Alignment consistency: Real tables have consistent column baselines across multiple rows. 
   Spaced plain text has arbitrary word alignments. We can measure the variance of x-coordinates 
   in columns; low variance implies a structured table, regardless of cell sparsity.

---

Q4: Explain how Reciprocal Rank Fusion (RRF) works and why you chose it over score normalization.
A: Dense vector search uses Cosine Similarity (scores -1 to 1), while sparse BM25 search 
   uses unbounded scoring (typically 0 to 30+). Normalizing these scores to merge them 
   is extremely unstable. RRF solves this by ignoring raw scores and focusing solely on ranks. 
   The RRF score is calculated as `sum(1 / (60 + rank_i))` across both legs. The results are 
   then sorted by RRF score. It is robust, requires no parameter tuning, and fuses semantic 
   concepts with exact keyword matches perfectly.

[Cross-Question]: If a user queries a unique serial number (e.g., "Invoice ID: INV-992"), 
RRF might rank a semantically similar invoice higher because the dense model scored it 
highly, even though the sparse model returned the exact match at rank 1. How do you prevent 
dense noise from overriding exact keyword matches?
[Answer]: Standard RRF can sometimes suffer from dense noise on keyword-heavy queries. In 
production, we implement:
1. Query-type classification: If the query contains strict patterns (serial numbers, IDs, 
   dates), we increase the weight of the sparse retrieval leg (Weighted RRF).
2. Rank-cutoff or minimum score filtering: We filter out dense matches if the dense score 
   falls below a certain threshold.
3. Cross-Encoder Re-ranking: We feed the top 30 merged results through a Cross-Encoder model. 
   Cross-Encoders evaluate the query and document chunk together, ensuring that an exact 
   keyword match is prioritized over conceptual similarities.

---

Q5: Since Qdrant is running in embedded mode, how do you handle concurrency and database locking?
A: Embedded Qdrant writes directly to a local disk storage path. Under the hood, it locks the 
   SQLite/database files. If multiple processes (e.g. the FastAPI server and a separate background 
   ingestion script) try to instantiate a client simultaneously, it raises a lock error. We solved 
   this by implementing a singleton pattern (`get_qdrant_client(path)`) in `vector_store.py` that 
   reuses a single connection instance, and by designing the FastAPI server to handle ingestion 
   in-process.

[Cross-Question]: If your application grows and you need to support multiple servers running 
FastAPI behind a load balancer, how does your database architecture adapt?
[Answer]: Embedded mode is only suitable for single-process, local applications. For a 
production-scale system with multiple worker nodes, we would transition to Qdrant Server. 
Because Qdrant client is highly abstracted, this transition only requires changing the 
initialization parameter from `path="./qdrant_data"` to `url="http://qdrant-service:6333"` in 
`config.py`. All indexing, retrieval, and schema structures remain 100% identical.
